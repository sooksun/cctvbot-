# Alembic Migrations — Design Spec

**Date:** 2026-07-26
**Project:** `cctvbot`
**Status:** Approved for implementation planning
**Mode:** Backend infrastructure; versioned schema for prod (MySQL/MariaDB).

---

## 1. Purpose

Schema is created by `Base.metadata.create_all` at boot, so new columns (e.g. the
recent `Camera.enabled`) never apply to an already-deployed database — each change has
needed a hand-written `ALTER TABLE`. Introduce Alembic so schema changes are versioned
and applied with `alembic upgrade head`.

## 2. Scope

### In scope
- Alembic scaffolding: `alembic.ini`, `migrations/env.py`, `migrations/versions/`.
- Initial migration matching the current models (users, cameras incl. `enabled`,
  events incl. the `ix_events_status_created_at` composite index, audit_logs).
- Boot strategy: `create_all` for sqlite (tests/dev); MySQL relies on Alembic.
- Dockerfile.api runs `alembic upgrade head` before uvicorn.
- DEPLOY.md migration + adoption docs.

### Out of scope
- Data migrations; per-change autogenerate workflow docs beyond a short note.
- Changing the test harness (tests keep sqlite `create_all`).

## 3. Boot strategy

- **sqlite (tests/dev):** `init_db()` keeps `Base.metadata.create_all` — fast, no
  migration machinery for the in-memory test DB.
- **MySQL (prod):** `init_db()` does **not** create tables; Alembic owns the schema.
  The API container runs `alembic upgrade head` before serving (migrate-then-serve),
  so `docker compose up` still works out of the box.

`init_db()` becomes:
```python
def init_db() -> None:
    from app import models  # noqa: F401
    if settings.database_url.startswith("sqlite"):
        Base.metadata.create_all(bind=engine)
```

## 4. Alembic wiring

- `alembic.ini`: `script_location = migrations`; the URL is supplied by `env.py`
  (not hard-coded), so one config works for MySQL and the sqlite test/verify path.
- `migrations/env.py`:
  - add `apps/api` to `sys.path` so `app` imports work under the alembic CLI;
  - `from app.db import Base` + `import app.models`; `target_metadata = Base.metadata`;
  - read the URL from `app.config.settings.database_url` for both offline and online.
- `migrations/versions/0001_*.py`: the initial migration, autogenerated from the models
  then verified. It must render dialect-agnostically (`sa.String(length=…)`, `sa.JSON()`,
  `server_default=sa.func.now()`, etc.) so it applies to both MySQL and sqlite.

## 5. Adoption path (documented in DEPLOY.md)

- **Fresh DB:** `alembic upgrade head` (or the container CMD) creates everything.
- **Existing DB created by the old `create_all`:** tables already exist. Bring it under
  Alembic once with `alembic stamp head` (ensure any pre-Alembic manual columns — e.g.
  the earlier `enabled` `ALTER` — are already applied so the schema matches head).
  Alternatively recreate the DB (pilot data is disposable).

## 6. Dockerfile

`apps/api/Dockerfile` copies `alembic.ini` + `migrations/` and runs migrations before
the server:
```dockerfile
COPY alembic.ini .
COPY migrations ./migrations
CMD ["sh", "-c", "alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port 8000"]
```

## 7. Testing (no MySQL required)

- Point `DATABASE_URL` at a temp sqlite **file**, run `alembic upgrade head` → assert the
  four tables exist; `alembic downgrade base` → gone.
- `alembic check` → no diff (the migration matches the models — guards against drift).
- Existing pytest suites stay green (in-memory sqlite via `create_all`): API 60, worker 90.

## 8. Risks & mitigations

| Risk | Mitigation |
|------|------------|
| Migration/models drift over time | `alembic check` in CI/dev flags it; documented "regenerate on model change". |
| Dockerfile CMD path resolution not verifiable here | Standard migrate-then-serve pattern; alembic itself verified on sqlite; flagged for first real container build. |
| Existing prod DB conflicts with `upgrade head` | Documented `alembic stamp head` (or recreate) adoption path. |
| Boot no longer creates tables on MySQL | Container runs `alembic upgrade head` first; deploy docs updated. |
